# 14 — Risks & Trade-offs

Individual decisions are justified next to where they're made throughout this document set, on the view that a trade-off explained beside its decision is more useful than one filed away in a generic list. This document does two things a per-section treatment can't: surface **risks** that cut across multiple layers, and give a **single scannable table** of the biggest cross-cutting trade-offs for quick reference.

## 1. Cross-cutting risks

| Risk                                                              | Impact                                                                                                             | Mitigation                                                                                                                                                            | Where                                                                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| LLM cost overrun                                                  | Runaway spend from a misbehaving workflow or capability loop                                                       | `usage_ledger` + per-org/project budget gates in the Model Router; rate limiting at the API layer as a second, independent gate                                       | [06](06-model-router.md), [08](08-api-design.md) §5                      |
| LLM output unreliability in engineering-critical decisions        | A hallucinated architecture decision or a subtly wrong bug fix gets acted on                                       | Mandatory human approval gates on critical/irreversible nodes; every decision is versioned and reversible (ADR supersede pattern, not overwrite)                      | [03](03-workflow-engine.md) §5, [05](05-memory-engine.md) §4             |
| Prompt injection via untrusted content, with real tool access     | Highest blast-radius risk in the system — see dedicated treatment                                                  | Least-privilege tool scoping, untrusted-content tagging, structural (not prompt-level) approval gates, sandboxed execution                                            | [12](12-security-architecture.md) §4                                     |
| Polyglot monorepo tooling complexity (pnpm + uv + turbo + Docker) | Real onboarding cost for new contributors                                                                          | `Makefile` as a single command surface regardless of which half of the stack is touched                                                                               | [01](01-repository-structure.md) §6                                      |
| Single-provider dependency (Gemini only at launch)                | Provider outage or pricing change has no fallback                                                                  | Model Router is provider-agnostic in its abstraction from day one, even with one provider configured — adding a second is a config + adapter change, not a redesign   | [06](06-model-router.md) §2                                              |
| Workflow Engine is the highest-novelty component                  | If its core design (LangGraph + Postgres checkpointing + interrupts) has a flaw, everything downstream is affected | Sequenced first in the roadmap specifically to surface problems while the blast radius is small — see Phase 1 exit criteria                                           | [13](13-development-roadmap.md)                                          |
| `pgvector` has a scaling ceiling                                  | Recall latency/quality degrades at very large embedding volume                                                     | Interface-hidden behind `MemoryEngine.recall()` so a migration to a dedicated vector store doesn't touch calling code; documented revisit trigger, not a silent cliff | [05](05-memory-engine.md) §2                                             |
| Modular monolith can decay into a "big ball of mud"               | Module boundaries erode as more modules/engineers are added over time                                              | CI-enforced import-boundary linting — a module reaching into another module's internals fails the build, not just code review                                         | [01](01-repository-structure.md) §4, [10](10-backend-architecture.md) §1 |
| Build logs stored inline in Postgres                              | Doesn't scale to high-volume/long-retention logging                                                                | Explicit size cap now; documented migration to object storage/log aggregation if outgrown                                                                             | [07](07-database-schema.md) §6                                           |

## 2. Major trade-offs, decided

| Decision                | Chosen                                                             | Alternative(s) considered                      | Why chosen                                                                                                                                                                               | Revisit when                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Service topology        | Modular monolith (`apps/api` + `apps/worker`, shared `services/*`) | Microservice per layer                         | Microservices split before any layer's boundaries are proven adds coordination/deployment overhead with no scaling benefit yet — nothing is under load that requires independent scaling | A specific layer (worker/execution is the likely first candidate) needs independent scaling the monolith can't give it         |
| Semantic memory storage | `pgvector` in the primary Postgres DB                              | Dedicated vector DB (Pinecone/Weaviate/Qdrant) | Avoids a second stateful system to operate/back up/reconcile; enables joining vector search with structured filters in one query                                                         | Embedding volume or query latency crosses a threshold where `pgvector`'s ANN index measurably degrades                         |
| Model Router policy     | Rule-based, config-driven                                          | Learned/adaptive routing                       | Explainability — a rule-based decision is auditable in the same way every other AI decision in the system must be; an adaptive router would need its own explanation layer               | Enough execution history exists to train a router, and it can be built as an explainable, opt-in layer rather than a black box |
| Realtime transport      | Server-Sent Events                                                 | WebSocket                                      | All current realtime needs are server→client only; SSE is plain HTTP, simpler to operate, auto-reconnects                                                                                | A feature needs genuine low-latency bidirectional traffic (e.g., collaborative editing)                                        |
| Hosting                 | Railway (backend/data) + Vercel (frontend)                         | Raw cloud (AWS/GCP)                            | Matches the brief's stated phasing (cloud providers are future phases); managed platforms trade some control for materially faster iteration at this stage                               | Scale, compliance, or cost profile makes managed-platform pricing/limits a binding constraint                                  |
| Background jobs         | Arq (asyncio-native, Redis-backed)                                 | Celery                                         | Matches the async-first backend; no new infrastructure (reuses Redis); simpler configuration                                                                                             | Job ecosystem complexity outgrows Arq's feature set (e.g., needs multi-broker support, richer scheduling/monitoring tooling)   |
| Multi-tenancy           | Shared DB/schema + `org_id`/`project_id` scoping + Postgres RLS    | Schema-per-tenant or DB-per-tenant             | Meaningfully simpler operations (one set of migrations, one connection pool) with isolation guarantees RLS already provides                                                              | A specific enterprise customer contractually requires physical data isolation                                                  |

## 3. What would make this architecture wrong

Worth stating plainly: this design optimizes for a small founding team shipping a genuinely novel orchestration layer (the Workflow Engine) as fast as possible while keeping the door open to scale later. If the actual starting conditions are different — e.g., enterprise compliance requirements exist from day one, or the team is large enough that microservice coordination overhead is already worth paying for its independent-deploy benefits — several decisions above would flip immediately (multi-tenancy would start at schema-per-tenant; service topology might start more decomposed). Flagged explicitly so the trade-off table above is read as "right for the stated context," not "right unconditionally."
