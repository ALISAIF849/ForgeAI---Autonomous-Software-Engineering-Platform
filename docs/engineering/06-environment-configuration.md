# 06 — Environment Configuration

## 1. Principles

- **`.env.example` files are committed; populated `.env`/`.env.local` files are never committed** — enforced by `.gitignore`'s explicit `!.env.example` exception (everything else matching `.env*` is ignored).
- **`apps/api` and `apps/worker` share one variable set** — both are backend processes needing the same DB/queue/provider access ([docs/architecture/02-service-architecture.md](../architecture/02-service-architecture.md) §3). Their `.env.example` files are intentionally near-identical; if they diverge, that's a signal one process needs a credential the other doesn't, and the divergence should be deliberate, not accidental.
- **`NEXT_PUBLIC_` is a security boundary, not a naming convention.** Anything with that prefix is bundled into client-side JavaScript and readable by anyone who opens browser devtools. A value gets that prefix if and only if it's genuinely safe to be public (a base API URL, a public OAuth client ID). It is never added to silence a build error — if Next.js complains a value isn't available client-side, the fix is to fetch it server-side, not to make it public.
- **Where real values live, per environment:** local dev → `.env.local` (gitignored, populated manually from the team's secret-sharing channel — a password manager team vault, not Slack/email in plaintext); staging/production → Railway's and Vercel's built-in environment variable stores ([docs/architecture/11-deployment-architecture.md](../architecture/11-deployment-architecture.md) §6), never a file in the repo at all.

## 3. Frontend (`apps/web`)

| Variable                             | Dev                       | Staging/Prod                 | Sensitivity                                                          |
| ------------------------------------ | ------------------------- | ---------------------------- | -------------------------------------------------------------------- |
| `NEXT_PUBLIC_API_BASE_URL`           | `http://localhost:8000`   | Real staging/prod API origin | Public                                                               |
| `NEXT_PUBLIC_SSE_BASE_URL`           | `http://localhost:8000`   | Real staging/prod API origin | Public                                                               |
| `NEXT_PUBLIC_GITHUB_OAUTH_CLIENT_ID` | Dev OAuth app's client ID | Per-environment client ID    | Public (client ID only — the secret half stays backend-only, see §2) |
| `NEXT_PUBLIC_SENTRY_DSN`             | Optional locally          | Required                     | Public (DSNs are designed to be client-exposed)                      |
| `NEXT_PUBLIC_ENVIRONMENT`            | `development`             | `staging` / `production`     | Public                                                               |

No backend secret ever gets a `NEXT_PUBLIC_` mirror "for convenience" — if the frontend needs data that requires a secret to fetch, it goes through a backend endpoint that holds the secret server-side, never by exposing the secret itself to the client.

## 4. Adding a new environment variable — the checklist

1. Does it need to be different per environment (dev/staging/prod)? If not, it's a constant in code, not an env var.
2. Is it a secret? If yes: never a default value in `.env.example` beyond an empty string, and it must go through the same "distinct value per environment" rule as everything marked Secret above.
3. Does the frontend need it? If yes, and it's genuinely safe to expose, `NEXT_PUBLIC_` prefix. If it's not safe to expose but the frontend needs the _result_ of using it, add a backend endpoint instead — don't reach for the prefix as a shortcut.
4. Add it to the relevant `.env.example` with a comment if its purpose isn't obvious from the name, and add a row to this document in the same PR — an env var that exists in code but not in `.env.example`/this catalog is exactly the kind of drift [12-documentation-standards.md](12-documentation-standards.md) exists to prevent.
