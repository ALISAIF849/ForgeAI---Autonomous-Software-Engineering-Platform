## 2. Why lint/test/build are separate workflows rather than one big job

Separate workflow files (or at least separate jobs within one workflow) let GitHub run them in parallel and report failures independently — a lint failure shouldn't block a developer from seeing whether tests also pass, and vice versa. It also means Turborepo's remote cache can be scoped per task type cleanly, and a flaky test suite doesn't block a trivial lint-only PR (like a typo fix in a comment) from getting fast feedback on the part of the pipeline that actually matters for that change.

## 3. What's deliberately left undecided here

- **Exact coverage threshold enforcement** — a hard gate ("PRs must not drop coverage below X%") is easy to add once there's a real baseline to set it against; setting one now, against zero existing tests, would be an arbitrary number. Revisit once Phase 1 ([docs/architecture/13-development-roadmap.md](../architecture/13-development-roadmap.md)) has shipped real test suites to baseline from.
- **Changelog/release automation tooling** (`release-please` vs. `changesets` vs. hand-rolled) — noted as undecided in [04-git-strategy.md](04-git-strategy.md) §4 too; both are reasonable, the choice doesn't block anything else in this document and is better made when the workflows are actually implemented.
- **Remote cache provider for Turborepo** (Vercel Remote Cache vs. self-hosted) — a reasonable default is Vercel's, given `apps/web` is already deploying there, but this is a small, easily-changed configuration knob, not an architectural decision worth locking in now.

## 4. Relationship to branch protection

This pipeline is only an enforced gate if [04-git-strategy.md](04-git-strategy.md) §5's branch protection rules are actually configured once a GitHub remote exists — a designed pipeline with no branch protection behind it is advisory, not a gate. Both are tracked as Sprint 0 checklist items together, deliberately, so one doesn't get set up without the other.
